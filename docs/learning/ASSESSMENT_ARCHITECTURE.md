# Phase 2.6 — Assessment architecture
Proposed refinement of DATABASE_ARCHITECTURE, COMPLETION_ARCHITECTURE and frontend ASSESSMENT_REVIEW_DESIGN. No code or tests.
## Question registry and scoring
Strict Zod discriminated schemas for prompt, private grading config, response and feedback. Stable option UUIDs, unique IDs, no answer keys in learner DTO. R1 single choice and true/false exact match; multiple choice exact set equality (order independent, duplicates rejected, no partial credit); numerical decimal string with bounded digits/exponent, finite values, inclusive absolute or relative tolerance (relative to absolute expected value; zero expected requires absolute tolerance), exact decimal arithmetic via vetted library or bounded scaled integers, no binary float comparisons; fixed displayed unit, no conversion R1. Short answer explicit accepted strings with NFC normalization, trim and optional case-insensitive matching using documented locale-independent policy; no fuzzy/AI grading. Alternatively self-review against model answer/rubric, integer awarded points 0..max, explicitly labeled self-reviewed. Unanswered earns zero; invalid response rejected rather than graded. No negative marking. R2 partial credit, matching, ordering, cloze, long form and banks.
Points integer 1..100 per question, max 100 questions provisional; sum earned/possible; basis points floor(10000*earned/possible) for display/storage, pass via exact integer cross multiplication earned*10000 >= threshold*possible. No empty published assessment. Pending self-review has no final normalized score; objective subtotal separately labeled. Best valid score order by exact ratio where needed, not rounded display; ties deterministic finalized_at then id. Self-reviewed evidence visible and eligible when configured, never described as independent verification.
## Revision and compatibility
Draft mutable separately from published immutable revisions (add draft representation or draft status and publish transaction in schema reconciliation). Publishing atomically sets active revision; questions and options snapshot. Add grading compatibility identity computed from canonical semantic config: question identities, prompts (conservative exact canonical comparison), options, correct keys, points, tolerance, review policy and grading algorithm version. Only explicitly nonsemantic changes such as order, explanation, display title or threshold preserve compatibility; threshold changes evaluate old compatible earned/possible against current threshold, historical pass uses original threshold. Timer/hint/feedback conditions affecting evidence invalidate compatibility conservatively. Never trust client compatibility claim. Preserve old attempts; in-flight attempts finish against original revision but may not satisfy current gate. Archive required linked assessment only with explicit gate removal/replacement in same transaction. Add stable logical question ID distinct from revision row ID.
## Attempts
States in_progress -> pending_review or finalized; in_progress -> abandoned; invalidation explicit audited flag/reason on finalized result, not deletion. Timed attempts have server deadline from start, no pause; server accepts answer saves only before deadline, on expiry finalizes last acknowledged answers (unanswered zero) via lazy finalization on access/submit or bounded sweeper; no client timestamps as authority. Deadline equality expired; use database clock after acquiring lock. One active in_progress attempt per enrollment/assessment via partial unique index; resume existing, explicit abandon to restart. Pending review may coexist with later attempts subject to quota. Untimed resume until explicit abandon or lifecycle policy. Store question/option presentation order snapshot if shuffled; R1 fixed order default. Flags persisted separately or in answer metadata, never grading input. No pre-submit keys, hints cannot expose answer unintentionally; feedback policy after finalization or explicit self-review stage. Owner-author can inspect keys in edit mode; not proctored.
## Transaction protocol
Guide lock then assessment/attempt lock, recheck owner, enrollment, lifecycle, revision and deadline. Start binds published revision; answer desired-state mutation expected attempt revision and operation ID; final submit includes expected revision and optional final answer batch, atomic validation/save/grade/status/event. Expired submit ignores unsaved batch and returns authoritative expiry result explicitly. Duplicate final submit returns same result, conflicting payload/operation ID rejected; never create second attempt. Self-review locks pending attempt, validates per-question awards and expected revision, finalizes only when all reviews complete; immutable final result, audited invalidation only. Reuse shared idempotency policy to be specified. No external calls in transaction. Read DTOs distinguish draft, learner, self-review and result; no grading secrets in logs or caches.
## Schema amendments and budgets
Add deadline_at, terminal_reason, invalidated_at/reason, compatibility identity, original threshold snapshot via revision FK, stable question identity, optional presentation snapshot, review timestamps and draft lifecycle. State checks and composite FKs; unique active attempt; index enrollment/assessment/status/compatibility via revision join. Provisional 100 questions, 100 points each, 20 options, 8 KiB response, 1 active attempt, rate limits and total retention/quota to be decided in performance/security milestone. Do not silently purge attempts.
