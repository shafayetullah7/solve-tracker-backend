# Phase 2.9 — Security, concurrency and recovery
Proposed R1 contract, no implementation. Reviewed actual AuthSecurityGuard, AccessGuard, API_ARCHITECTURE and MEDIA_PRIVACY_ARCHITECTURE. Existing guard sets private/no-store and no-referrer, checks mutation Origin and X-Requested-With practice, JSON except POST /media multipart; existing limiter is process-local and covers selected auth/media routes, not general learning traffic.
## Authorization and threat boundaries
Reuse guards in existing order, derive actor from req.auth.user.id; every repository operation scoped by actor and aggregate, nested composite FKs supplement but never replace access checks. Owner-only R1 enrollment; no Discover/public search exposure. Separate author/learner/review DTOs; no grading keys in active attempt. Deleted resources inaccessible except explicit recovery routes; archived read/export only. Check lifecycle and ownership again inside mutation transaction. Cross-account 404, CSRF 403, preserve auth errors. Never accept client owner IDs. Audit export, restore, media content and import preview as carefully as CRUD. GET/HEAD read-only; review existing guard HEAD behavior before adding HEAD routes. Verify reverse proxy trusted IP/origin configuration, cookie settings and actual SSR cache behavior before release.
## Concurrency and transactions
Canonical lock order: account lifecycle/quota lock when required, sorted guide IDs, sorted node IDs, block/assessment/attempt rows in documented operation order, sorted media IDs. Never acquire earlier lock after later; cleanup media-only cannot subsequently acquire guide/account lock. Account erasure coordinates with all writers using account lifecycle barrier; implementation must prove race safety, choose shared account row lock for normal writes and exclusive for erasure or equivalent. Guide row lock serializes structural and learning writes initially; recheck revision after lock. PostgreSQL READ COMMITTED plus explicit locks for mutations; consistent read snapshot for aggregate progress. No provider/network calls inside transaction. Bounded lock/statement timeouts; retry whole transaction only on known rollback (deadlock/serialization), max two retries with jitter and same operation identity; ambiguous commit reconcile, never blind retry. Lock contention surfaced as retryable failure, not stale revision unless verified. Verify real PostgreSQL concurrent tests.
## Idempotency
Proposed learning_operations table actor_id, operation_id UUID unique per actor, action, resource scope (canonical path or create collection), request_hash, outcome status, minimal result reference/revision, created_at, expires_at. Canonical validated payload including expected revision and scope, hash versioned; no raw content or answer keys. Acquire operation reservation in same transaction as domain writes, after account authorization and before domain revision check; concurrent same ID waits then resolves committed outcome; rollback removes reservation. Recheck current authorization on replay, including deletion recovery semantics; same ID different hash/scope 409; return minimal original receipt or explicit reconcile with current resource, never pretend current state equals original response. Creation receipts preserve created ID. DELETE replay authorized via owner-scoped tombstone/receipt. No external calls under reservation; media uses durable intent state machine. Proposed 7-day receipt retention, bounded per-account count and cleanup; clients must not automatically retry after expiry, reconcile first. Durable natural uniqueness for final submission/import commit and upload intent independent of receipt expiry; import preview consumed marker retained for retry horizon. No guarantee of exactly-once arbitrary create after receipt expiry. Rate limits and quotas apply to new operations; replay also bounded.
## Abuse and content safety
Add authenticated per-user route-class limits after access guard, IP limits at trusted edge, global concurrency and bounded queue for import/export/media/large queries. Provisional 120 reads/min, 120 ordinary mutations/min, 10 imports/hour, 10 exports/hour, 30 attempt starts/hour; tune with autosave and benchmarks, return 429 Retry-After. Existing process-local limiter not distributed or sufficient for quota; single instance initially, DB-backed durable storage quotas; multi-instance requires shared rate policy. Enforce request byte limits before parsing, bounded JSON depth/counts, parameterized SQL, strict Zod, safe URL schemes, trusted AST renderer, math/diagram limits, no arbitrary remote fetch, no execution. CSP and no-referrer/no-store; inspect SSR/proxy headers. No private payloads, cookies, tokens, answer keys, signed URLs or note text in logs/traces. Structured request ID, route template, status, duration, safe error code; bounded retention and restricted access.
## Recovery and lifecycle
Local drafts in memory by default; optional account-scoped persistent recovery only after explicit consent, bounded TTL/size, clear on logout/account switch, never claim browser storage is encrypted or safe on shared device. Preserve local draft on 409, compare/reapply explicitly, stale acknowledgments cannot overwrite. On ambiguous save reconcile operation receipt/current revision. Recoverable guide/subtree deletion proposed 30 days; retain references and evidence, restore under locks, purge bounded batches after expiry, no silent attempt deletion. Account erasure blocks new writes, revokes sessions, removes personal rows and schedules durable provider deletion independent of user FK cascade; verify backup retention and legal policy, no promise of immediate backup erasure. Backups encrypted, restricted, off-host; proposed daily backup and 30-day retention, RPO 24h/RTO 4h provisional, restore drill including media manifest and migration compatibility; DB backup alone cannot restore destroyed provider bytes. Coordinate provider retention/export or disclose gap before release. No automatic restoration of deleted accounts from backup into live service; erasure reconciliation.
## Verification and rollout
Threat matrix: cross-owner nested IDs, stale revisions, duplicate operation, conflicting hash, replay after delete/revocation, concurrent move/delete/save/submit, account erasure race, lock timeout/deadlock, rollback, lost response, import bomb, XSS/SSRF, key leakage, quota race, media cleanup, restore drill, existing auth/profile/problem regression. Pure tests plus real PostgreSQL and HTTP integration, browser tests for recovery/auth epoch. Feature flag default off until baseline, privacy and migration gates pass. No new Redis/broker. Proposed limits, receipt retention, lock order details, account barrier and backup policy require reconciliation and runtime verification; no code/migrations/tests executed.
