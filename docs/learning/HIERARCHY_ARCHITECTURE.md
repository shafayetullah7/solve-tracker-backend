# Phase 2.3 — Hierarchy and ordering
Status: proposed refinement of DATABASE_ARCHITECTURE.md; no implementation. Adjacency list, same-guide composite parent FK, recursive CTEs, stable UUIDs. No closure table or materialized path initially.

## Read model
Load authorized guide metadata separately from content. Initial tree metadata may be fetched in one bounded query, assembled O(n) in memory by parent and position; lazy children for large trees, server-side search with ancestor paths. Recursive CTE for ancestors/subtrees/depth, parameterized SQL, explicit guide scope at every recursive term, visited path/depth guard for corruption. Deterministic preorder via sibling position path, not assumed CTE output order. No N+1 queries. Provisional limits: 32 levels (root depth 1), 5,000 active nodes per guide, 500 siblings; benchmark and adjust in performance milestone. Bound total retained/deleted records separately.

## Structural mutation protocol
All structural writers including import, restore, duplicate and delete lock owned active guide row FOR UPDATE first in transaction; recheck authorization/lifecycle and expected structure revision after lock. Read current siblings and subtree; reject stale revision with 409 and current revision. Move accepts node ID, destination parent nullable and before-sibling ID nullable (append), not arbitrary position. Validate anchor belongs to destination and is not moving node; reject cross-guide, self, descendant parent, depth overflow, sibling limit and invalid/deleted nodes. New maximum depth = destination parent depth + subtree height (root parent depth 0). Same-parent move removes moving ID before insertion. No-op leaves revision unchanged. Update parent and positions atomically; increment guide revision once. Return authoritative changed metadata/revision. All structural writes share lock protocol; no forwardRef or distributed lock. Content writes that may race deletion acquire guide lock before node/block locks, with finer granularity only after proof. Never hold locks across external calls.

## Ordering
Dense zero-based integer positions, root and nonroot partial unique indexes as prior spec. Avoid direct swaps under immediate uniqueness. Under guide lock, stage affected sibling rows into distinct temporary nonnegative positions above current maximum and final range; then move parent and assign final positions. For cross-parent moves choose temporary positions globally distinct across both affected groups, move node while staged, then finalize both lists. Bound staging arithmetic below int max; rollback on any failure. Only committed positions are dense. Same approach for block reorder under appropriate guide/node lock. Prefer simple bounded O(siblings) writes; benchmark before fractional ranks. No-op and failed operations do not increment revisions.

## Copy and deletion
Duplicate subtree with fresh IDs, explicit old-to-new map, remap internal links and checklist item IDs, copy authored assessment configuration as independent identity unless explicitly reusable in future; no personal notes, attempts, progress or events copied. Preserve authorized media references only after media lifecycle design. Cross-guide copy is explicit, locks guides in sorted UUID order; no cross-guide move in R1.
Refinement: propose recoverable subtree deletion via deletion batch UUID and deleted_at on nodes, preserving original parent/position metadata in batch records; active sibling indexes filter deleted_at IS NULL. Mark entire subtree atomically, compact active siblings, hide deleted blocks/notes through ancestor lifecycle. Restore entire batch under guide lock, validate active parent or choose new destination, append or explicit anchor, recheck limits. Preserve IDs and personal state; reevaluate requirements. Exact retention window, batch table and purge FK ordering require lifecycle/media review before migration. Never cascade deletion into assessment attempts. Guide archive read/export only; guide deletion hides aggregate. Resume fallback: next surviving preorder node, else previous, else null; update affected enrollments in same transaction. Purge explicitly removes expired content/notes and releases media; history policy and account erasure separately specified.
